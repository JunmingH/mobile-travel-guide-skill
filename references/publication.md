# 加密发布与升级

## 两个不同仓库

- **skill 代码仓库**：只含通用代码、模板、文档与虚构测试。可以开源。
- **某次旅行的发布仓库**：只含 `github-pages-build.json.files` 指定的加密发布资源。完整 Word/HTML、研究包、访问码、密钥、个人附件和用户账目不可上传。

不要把整个工作台 git add。使用专门暂存目录，逐项复制清单文件，先扫描和核对，发布后核对远程树/提交。旧加密块若为缓存过渡而保留，必须与前一份可信构建清单逐项匹配；不能放宽为“任何 bin 都可”。

## 加密机制和边界

完整 HTML（包括内嵌图片与运行时）分块 AES-256-GCM 加密；每次构建随机内容密钥，每块随机96-bit IV和关联数据；解密后复核全 HTML SHA-256。随机盐及 PBKDF2-SHA256 600,000 次将随机访问码派生为包装密钥，再加密内容密钥。

盐、IV、程序、加密元数据和应用名公开不等于公开密钥。任何人仍可下载密文并离线猜码，因此用密码管理器生成至少14位高熵随机码，建议20位以上；长度本身不是熵保证。不要使用生日/电话号码/短PIN。

每次重新加载需输入码，后台返回未必重新锁定。已解密副本、截图和已保存文件无法收回。更换访问码并不能撤销历史副本。本地账目/照片未单独加密；同源恶意脚本、账号/浏览器被控制不在静态文件加密能解决的范围内。高敏感订单号/证件资料可从公开分发的手册中移除，仅留设备上的原件。

## 构建

```sh
python scripts/mobile.py pwa /path/to/private-trip
python scripts/mobile.py encrypt /path/to/private-trip
python scripts/mobile.py verify /path/to/private-trip
```

访问码通过隐藏输入提供，不出现在命令参数中。自动化只用私有标准输入传 JSON；不要用可能回显的终端，也不要写临时“密码文件”。新构建生成新密文，必须重跑当前版本检查；不能用旧报告冒充新版本。

生成器先在专用暂存目录完成，再替换有可信清单的旧输出，并把旧版保留在私人 `.mobile-history/`。如果旧输出有陌生文件、修改或符号链接，停止替换并检查，不覆盖用户资料。

## GitHub Pages

用户已授权仓库及访问方式时直接执行，不重复确认。若尚未确定权限或是否公开明文，先准备可审阅加密包，再明确目标和公开范围。已有登录即可使用 connector / 已认证 CLI / 浏览器；不要读取浏览器 cookie 来构造认证。

1. 确认 GitHub 账号和目标仓库；更新时复用现有仓库。
2. `release_gate.py WORKBENCH` 通过后，只提交清单文件。提交信息保持通用，不放私人日期、航班或酒店。
3. 配置/沿用 Pages 的发布分支及目录，开启 HTTPS。等待此次提交的部署成功。
4. `mobile.py verify WORKBENCH --url https://OWNER.github.io/REPO/` 校验所有文件，不只检查首页200。
5. 新访客只见解锁页；原码可打开完整手册；旧缓存收到更新提示；确认更新后重新解锁并显示离线就绪。
6. 在私人 QA 中记录目标 URL、提交、构建版本、工作流和限制。公开仓库无需放这些含本地路径的报告。

GitHub Pages 上的新静态版本不会把其他人的本机记录同步过来。如用户要同行实时共享成员、账目、附件和还款，另行设计认证与存储服务；不能将静态发布描述为已完成云同步。

## 手机升级说明

联网打开原主屏幕图标 → 安装与设置 → 重新检查 → 等待“更新离线手册” → 点击更新 → 输入原码 → 等“离线已就绪”。下载较大时按钮会稍晚出现。普通升级不卸载应用、不清除网站数据。

首次添加到主屏幕后必须从新图标打开并完成缓存，不能只假定 Safari 标签页的缓存就是主屏幕应用缓存。
